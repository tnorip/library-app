# Requirements Workshop

`/library-interview` で収集した情報を、実装可能な要件定義へ変換するワークショップです。

## スキルの目的

- インタビューの「生の声」を構造化された要件へ変換する体験
- ユーザーストーリーの書き方を実践する
- MoSCoW法による優先度付けを体験する
- 設計フェーズ（ER図・API設計）へ接続できる形式でアウトプットする

---

## 実行フロー

### Step 0: インタビュー情報の確認

スキル起動時に以下を確認する:

```
📋 Requirements Workshop — みどり市立図書館
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

インタビュー情報を確認します。

以下のいずれかで情報を提供してください：
  A) 「前の会話を使って」→ 直前の /library-interview の内容を使用
  B) インタビューメモを直接ペースト

インタビューを実施した対象者を教えてください：
  □ 田中さん（司書）
  □ 佐藤さん（市民利用者）
  □ 山本さん（館長）
```

インタビューが1件の場合は進める。0件の場合は `/library-interview` を先に実行するよう促す。

### Step 1: ペインポイントの整理と分類

収集した情報から課題・不満・ニーズを抽出し、以下の軸で整理する:

```
🔍 Step 1: ペインポイント整理
━━━━━━━━━━━━━━━━━━━━━━━

【現場業務の非効率】（スタッフ視点）
- [抽出した課題を列挙]

【利用者体験の課題】（市民視点）
- [抽出した課題を列挙]

【運営・管理の課題】（館長視点）
- [抽出した課題を列挙]

複数ペルソナが言及した課題（重要度高）:
- [重複する課題があれば強調]

⚠️ インタビューで出てこなかった可能性のある観点:
- [引き出せなかった課題があれば指摘。デブリーフと連動]
```

次のステップへ進む前に: 「この整理でよさそうですか？補足や修正があれば教えてください」と確認する。

### Step 2: ユーザーストーリーの作成

整理したペインポイントをユーザーストーリー形式に変換する。受講者が自分でストーリーを書けるよう、最初の1〜2例を示してから残りを一緒に考える対話形式で進める:

```
📖 Step 2: ユーザーストーリー作成
━━━━━━━━━━━━━━━━━━━━━━━━━━

ペインポイントをユーザーストーリーに変換します。

【例】
> US-001: オンライン予約
> As a 図書館利用者（佐藤さん）
> I want to スマートフォンから図書の予約・更新・確認ができる
> So that わざわざ来館しなくても貸し出し管理ができる

---

次のストーリーを一緒に作りましょう。
[次のペインポイント]についてはどんなストーリーが書けそうですか？

（ヒント: 誰が / 何をしたいか / なぜそれが価値か、の3点を意識して）
```

ユーザーストーリーが全て揃ったら Step 3 へ進む。

### Step 3: 前提機能の洗い出し

MoSCoW に入る前に、ユーザーストーリーを実現するための「技術的前提」を受講者自身に気づかせる。このステップは答えを与えず、問いかけで進める:

```
🔧 Step 3: 前提機能の洗い出し
━━━━━━━━━━━━━━━━━━━━━━━━━━

ユーザーストーリーを実装するには、裏側でどんな「土台」が必要でしょうか？

例えば US-001「オンライン予約」を実現するには：
  → 予約できる「本」のデータがシステムに存在している必要があります
  → 本のデータはどこから来ますか？誰がどうやって登録・更新・削除しますか？

---

各ストーリーについて考えてみましょう：

  1. このストーリーを動かすには、どんなデータが事前に存在している必要があるか？
  2. そのデータは誰が作り、更新し、削除するか？
  3. その「データ管理機能」を実現するユーザーストーリーは、すでにリストにあるか？

（まだリストにない「前提機能」があれば、ここで追加してください）
```

受講者が「本のCRUD」「貸出記録の管理」等を自力で追加したら、その気づきを肯定する。
追加されなかった場合は「本のデータはどこから来ますか？」と一度だけヒントを出す。

前提機能がリストに揃ったら Step 4 へ進む。

### Step 4: MoSCoW 優先度付け

受講者に各ユーザーストーリーの優先度を判断させる。理由を聞くことで思考を促す:

```
🎯 Step 4: MoSCoW 優先度付け
━━━━━━━━━━━━━━━━━━━━━━

Must have（必須）: システムが機能するために絶対必要
Should have（重要）: 強くほしいが初期リリースなくても動く
Could have（あれば良い）: 余裕があれば含めたい
Won't have（今回はしない）: スコープ外

各ストーリーをM/S/C/Wに分類してください。
判断に迷う場合は「なぜそのカテゴリか」の理由も考えてみてください。

[ユーザーストーリーのリストを提示]

まず US-001 から: どの優先度だと思いますか？
```

全ストーリーの分類が終わったら確認してから Step 5 へ進む。

### Step 5: 受け入れ条件の定義（Must have のみ）

Must have に分類されたストーリーの受け入れ条件を具体化する:

```
✅ Step 5: 受け入れ条件の定義
━━━━━━━━━━━━━━━━━━━━━━━━

Must have の各ストーリーについて、「実装完了をどうやって確認するか」を具体化します。

【例】
> US-001: オンライン予約
> 受け入れ条件:
> - [ ] タイトル・著者名で本を検索できる
> - [ ] ログイン済みユーザーが予約ボタンで予約できる
> - [ ] 予約成功時にメール通知が届く
> - [ ] 予約一覧画面でキャンセルできる

---

[次のMust haveストーリー] の受け入れ条件を考えてみましょう。
「これができたら完成と言える」という視点で考えてみてください。
```

### Step 6: 要件定義書の生成

全ステップが完了したら、構造化された要件定義書を `docs/requirements-draft.md` に出力する:

```markdown
# 要件定義書（ドラフト）— みどり市立図書館管理システム

## 1. 背景・目的
[インタビューから得られたコンテキストを記述]

## 2. ステークホルダー
| ペルソナ | 役割 | 主な課題 |
|---------|------|---------|
| 司書（田中さん） | 日常業務担当 | [主な課題] |
| 市民利用者（佐藤さん） | エンドユーザー | [主な課題] |
| 館長（山本さん） | 意思決定者 | [主な課題] |

## 3. ユーザーストーリー一覧
[全ストーリーを US-001 から順に記述]

## 4. 優先度マトリクス（MoSCoW）
### Must have
[ストーリーと受け入れ条件]

### Should have
[ストーリー]

### Could have
[ストーリー]

### Won't have（今回のスコープ外）
[ストーリー]

## 5. 制約・前提条件
- 個人情報保護: 利用者データのセキュリティ最優先
- 運用体制: IT担当1名での運用保守が可能な範囲
- 段階的リリース: 2ヶ月後の第一次リリースに収まるスコープ

## 6. 未確認・要調査事項
[ワークショップ中に「確認が必要」となった項目]
```

出力後、以下を案内する:

```
📝 要件定義ドラフトを docs/requirements-draft.md に保存しました

次のステップ:
  要件定義書をもとに設計フェーズ（ER図・API設計）へ進んでください
```

---

## Claude への注意事項

- **対話形式を維持する**: 全部を一度に生成しない。ステップごとに受講者の入力を待つ
- **答えを与えない**: 「何がMustだと思いますか？」と聞く。受講者が考える時間を作る
- **理由を引き出す**: 「なぜそう思いましたか？」を繰り返してメタ認知を促す
- **インタビューの「抜け」を活かす**: 引き出せなかったニーズがある場合、「このペインポイントはインタビューでは出てきませんでしたが、実際には重要な可能性があります」と指摘する
- **技術的実現可能性は問わない**: このワークショップは要件定義。実装詳細は次フェーズ
- **完璧を求めない**: ドラフトは不完全で良い。「実装しながら更新する前提」と伝える
